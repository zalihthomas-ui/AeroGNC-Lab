# FMI Interoperability Preparation

## Scope

AeroGNC-Lab provides a deterministic FMI 3.0 Co-Simulation interface contract for
the fictional quaternion attitude controller. The contract is generated by
`aerognc.interoperability.fmi_interface` and stored under
`fmi_validation/attitude_controller_interface`. It defines scalar-first
body-to-NED reference and measured quaternions, forward-right-down body angular
rates, synthetic proportional/rate-damping/limit parameters, and body moment
commands. Value references are unique, dependencies are explicit, and units are SI.

The design follows the official [FMI 3.0.2 specification](https://fmi-standard.org/docs/3.0.2/).
FMI defines Model Exchange, Co-Simulation, and Scheduled Execution. A controller
with a sampled communication boundary maps naturally to Co-Simulation preparation;
the contract declares a preferred fixed 10 ms internal/communication step. FMI 3
supports arrays, but this first contract intentionally exposes scalars to make axis,
order, sign, and unit review obvious across a broad range of importing tools.

## Honest artifact status

The XML is not an FMU. A distributable Functional Mock-up Unit is a ZIP archive that
must contain `modelDescription.xml` plus the C API implementation as platform
binaries and/or source, along with any required resources. AeroGNC-Lab has not yet
implemented that mandatory C wrapper, built an `.fmu`, run the official XSD/checker,
imported an FMU into another simulator, or executed a numerical equivalence case.
`STATUS.json` records every one of those outcomes as false so the interface review
cannot be mistaken for external runtime validation.

The local validator checks XML parsing, FMI version and model identifier, stable
variable names/order/count, unique value references, causalities, and complete
`ModelStructure` output declarations. Those checks are useful software evidence but
are not represented as official FMI schema certification.

## Reproduction

Generate the same contract and status record with:

```powershell
python -m aerognc.cli fmi-interface
```

The output contains no timestamp, host path, or platform-dependent identifier, so
repeated generation is byte-reproducible. Automated tests mutate the FMI version to
confirm rejection and inspect the non-FMU status flags.

## Planned executable path

1. Freeze a narrow controller ABI and compare it directly against the Python law.
2. Implement the FMI 3 C API for Co-Simulation without embedding the Python runtime.
3. Build source and platform-specific binary variants in isolated CI jobs.
4. Package the complete FMU archive and run the official FMI validation tooling.
5. Import it into at least one independent compatible simulator.
6. Replay deterministic quaternion/rate vectors and compare moment commands against
   Python at strict numerical tolerances.
7. Measure initialization, communication-step, allocation, and worst-case timing.

Until those steps are performed, documentation will continue to say “FMI interface
contract” rather than “FMI implementation” or “validated FMU.” This boundary is
separate from MATLAB/Simulink validation and from the software-only future-HIL packet
loopback; none is used to imply physical hardware testing.
